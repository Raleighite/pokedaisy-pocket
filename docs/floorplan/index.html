A newcomer tour of the existing native path and the four requested handheld ports.

Follow a game from launch to exit

  1. Firmware launches the host. The existing PortMaster launcher prepares the firmware's input environment and starts the native application. Miyoo launch integration is still unimplemented.
  2. The host chooses a core. The SDL2 host presents the game list and loads the appropriate libretro library. A Linux executable and its cores must match the target CPU and firmware ABI.
  3. The core runs the game and companion. Emulator state is read through the integration layer. The portable companion draws its screens using game-specific data. A generic stock emulator core alone does not supply that integration.
  4. The host handles sound, controls and persistence. Its menu and save helpers handle user paths that must be tested independently of rendering.
  5. Normal exit must preserve progress. Each future device package needs a real in-game save, normal exit and reload test. Do not point an unqualified package at live saves.

1. Native host: the application's front door

linux/main.c handles the library, controller events, frame pacing, sound and dynamically loaded cores. linux/CMakeLists.txt requires SDL2. Firmware integration is separate from the emulator itself.

Read host source
2. Emulator bridge: why this is more than an overlay

libretro/pd_libretro.c connects emulator execution with companion behavior. The mGBA build is described by libretro/CMakeLists.txt; the separate armGBA GBA build by libretro/armgba/CMakeLists.txt. Backend choice needs both performance and memory-reader compatibility.

Read bridge source
3. Companion: information and menus

3ds/core/ contains portable companion components reused by the native Linux path. Reuse is preferable to rebuilding the Android UI on a small Linux device. A controller-first Pocket presentation is a target, not an implemented redesign.

Explore companion sources
4. Persistence: saves are a separate acceptance gate

linux/host_io.c provides host I/O helpers; the host owns battery-save and state handling. Existing tests are useful evidence but do not establish power-loss or suspend safety on a new device.

Read persistence helpers
5. Firmware packaging: one launcher does not fit every OS

linux/portmaster/PokeDaisy.sh is existing PortMaster integration. linux/package.py assembles upstream native packages. Neither proves support for Onion, a particular muOS release, stock Anbernic firmware or lid events.

Read launcher source

Four devices, two platform investigations

Miyoo Mini Plus and Miyoo Mini v4

Investigate 32-bit ARM SDK/ABI, an appropriate core backend and the firmware's SDL/display path. Mini v4 additionally needs resolution acceptance; the documented 752x560 mode depends on firmware. No target build or physical test has passed.

Anbernic RG34XXSP and RG35XXH

Both use H700 Cortex-A53 according to manufacturer specifications. The existing AArch64 native path is a starting point, not a compatibility guarantee. Qualify the installed firmware. Separate screen layouts are required for the specified 720x480 and 640x480 panels. RG34XXSP lid behavior remains untested.

Scope and upkeep

This is a curated native-architecture map, not a file-by-file census of the inherited Android app, website, translations, 3DS port or vendored emulator code. Those remain outside this map's coverage. No production deployment is described.
